# पहले एक ज़रूरी बात साफ़ कर दूँ

**Play Store से update करने पर Android आपके ऐप का data मिटाता नहीं है।**

जब तक signing key वही है (आपकी `prokisan-upload.jks`) और versionCode बढ़ा
हुआ है, Android पूरा `/data/data/com.prokisan.app/` फ़ोल्डर **ज्यों का त्यों**
रखता है — SQLite database, settings, सब।

तो सवाल "update में data खोएगा?" का सीधा जवाब है: **अपने आप नहीं खोएगा।**

**असली ख़तरा update नहीं, ये चार हैं:**

1. migration में ग़लती — कोड नया column माँगे जो पुराने DB में है ही नहीं
2. database का नाम बदल जाना — ऐप नई ख़ाली फ़ाइल देखने लगे
3. **अधूरा backup restore हो जाना** ← यहाँ असली गड़बड़ी मिली
4. फ़ोन बदलना / ऐप uninstall करना

# 🔴 गड़बड़ी 1 — Backup में आधा data ही जाता है (सबसे ज़रूरी)

`backup_service.dart` का `_generateBackupPayload()` सिर्फ़ **चार** चीज़ें
उठाता है:

```dart
customers · entries · payments · settings
```

पर database में **नौ** tables हैं:

| Table | backup में? | किसान के लिए इसका मतलब |
|---|---|---|
| `customers` | ✅ | ग्राहक |
| `entries` | ✅ | दूध की रोज़ की एंट्री |
| `payments` | ✅ | जमा-बाक़ी |
| `settings` | ✅ | सेटिंग |
| **`pashu`** | ❌ | **मेरे पशु — नाम, टैग, AI की तारीख़, ब्याने की तारीख़, टीके** |
| **`saved_fields`** | ❌ | **GPS से नापे हुए खेत** |
| **`dairy_product_entries`** | ❌ | **घी/पनीर/खोया के हिसाब** |
| `saved_news` | ❌ | सहेजी हुई ख़बरें |
| `news_cache` | — | सिर्फ़ cache, न जाए तो चलेगा |

**नतीजा:** किसान ने backup लिया, फ़ोन बदला, restore किया — तो उसके **सारे
पशु, नापे हुए खेत और घी-पनीर का हिसाब ग़ायब**। और उसे पता भी नहीं चलेगा,
क्योंकि restore "सफल" कह देगा।

पशु वाला हिस्सा सबसे भारी है — उसमें **ब्याने और टीके की तारीख़ें** हैं, जो
किसान ने महीनों में जमा की होती हैं।

> एक राहत: `restoreFromDetectedBackup()` सिर्फ़ चार tables को `delete` करता
> है, इसलिए **उसी फ़ोन पर** restore करने से पशु/खेत मिटते नहीं। मार तब पड़ती
> है जब नए फ़ोन पर restore हो — वहाँ वे कभी पहुँचते ही नहीं।

# 🔴 गड़बड़ी 2 — पशु की फ़ोटो backup में है ही नहीं

फ़ोटो यहाँ रखी जाती है:

```
app_flutter/pashu_photos/pashu_1234.jpg
```

पर `backup_rules.xml` में सिर्फ़ यह लिखा है:

```xml
<include domain="file" path="ProKisan_Backups" />
```

यानी **`pashu_photos` फ़ोल्डर छूट गया है।**

साथ ही database में फ़ोटो का **पूरा रास्ता (absolute path)** रखा है:

```
/data/user/0/com.prokisan.app/app_flutter/pashu_photos/pashu_1234.jpg
```

नए फ़ोन पर वह रास्ता हो ही नहीं सकता। तो restore के बाद पशु तो दिखेंगे पर
**फ़ोटो की जगह टूटा हुआ निशान** आएगा।

# 🟡 गड़बड़ी 3 — `onDowngrade` नहीं है

अगर कभी versionCode पीछे चला जाए (Play Store पर rollback, या किसान पुरानी
APK साइड-लोड कर ले), तो sqflite अपवाद (exception) फेंकता है और **ऐप खुलेगा
ही नहीं**।

data मिटता नहीं, पर ऐप बेकार हो जाता है — किसान को लगेगा सब चला गया।

# 🟡 गड़बड़ी 4 — migration की कोई जाँच नहीं

अभी 7 migrations हैं और एक भी test नहीं। आगे migration 8, 9, 10 लिखेंगे तो
पता ही नहीं चलेगा कि पुराने DB पर वे चलते भी हैं या नहीं — जब तक किसी असली
किसान का ऐप न टूटे।

# ✅ योजना — क्या-क्या करना है

## क़दम 1 — Backup में सारे tables डालो 🔴

`_generateBackupPayload()` और `restoreFromDetectedBackup()` दोनों में जोड़ें:
`pashu` · `saved_fields` · `dairy_product_entries` · `saved_news`

**साथ में backup का version `1.0.0` → `2.0.0` करें**, और restore को ऐसा बनाएँ
कि **पुरानी (1.0.0) backup फ़ाइल भी चलती रहे** — जिस किसान के पास पुरानी
backup पड़ी है, उसका restore टूटना नहीं चाहिए।

> ⚠️ **restore का तरीक़ा बदलना ज़रूरी है।** अभी वह पहले `delete` करता है फिर
> डालता है। अगर बीच में कुछ टूटा तो किसान का data आधा मिट चुका होगा। इसे
> "पहले पूरा पढ़ो और जाँचो, तभी हाथ लगाओ" वाला बनाना है।

## क़दम 2 — फ़ोटो बचाओ 🔴

दो हिस्से:

**(क)** `backup_rules.xml` और `data_extraction_rules.xml` में जोड़ें:
```xml
<include domain="file" path="pashu_photos" />
```

**(ख)** database में **पूरा रास्ता रखना बंद करें** — सिर्फ़ फ़ाइल का नाम
(`pashu_1234.jpg`) रखें और दिखाते समय फ़ोल्डर जोड़ लें। तब फ़ोन बदलने पर भी
फ़ोटो मिल जाएगी।

पुराने पूरे रास्तों को migration में छोटा कर दें (आख़िरी `/` के बाद वाला
हिस्सा रख लें) — जिनका ऐप पहले से लगा है उनका भी ठीक हो जाए।

## क़दम 3 — `onDowngrade` लगाओ 🟡

`onDowngrade: onDatabaseDowngradeDelete` **मत** लगाइए — वह data मिटा देता है।

इसकी जगह एक ऐसा handler रखें जो **कुछ न करे** (`async {}`)। तब पुराना ऐप नए
DB को खोल लेगा; उसे जो नए column नहीं पता, उन्हें वह छुएगा नहीं। data बचा
रहेगा और ऐप खुल जाएगा।

## क़दम 4 — migration की जाँच लिखो 🟡

एक test जो असली में करके देखे:

1. version 1 का DB बनाओ, उसमें कुछ ग्राहक/एंट्री डालो
2. उसी फ़ाइल को version 7 के कोड से खोलो
3. जाँचो कि **पुराना data ज्यों का त्यों है** और नए columns भी आ गए

यही 5 → 7, 6 → 7 के लिए भी। तब आगे कोई migration तोड़ेगा तो तुरंत पकड़ा
जाएगा — किसी किसान का ऐप टूटने से पहले।

## क़दम 5 — रिलीज़ से पहले की छोटी checklist 🟢

हर update से पहले तीन बातें:

- [ ] database का नाम बदला तो नहीं? (`dudh_ka_hisab.db` वही रहे)
- [ ] नया column/table जोड़ा तो `_schemaVersion` बढ़ाया और `_onUpgrade` में
      लिखा? (सिर्फ़ `_onCreate` में लिखना **सबसे आम ग़लती** है — नए install
      पर चलेगा, पुराने पर नहीं)
- [ ] `flutter test` में migration वाली जाँचें पास?

# ✅ जो सचमुच हुआ (7 अगस्त 2026)

## 1. Backup अब पूरा — 4 से 8 tables

`pashu` · `saved_fields` · `dairy_product_entries` · `saved_news` जुड़ गए।

अब हर table **सीधे SQL से** पढ़ा जाता है, model के `toMap()` से नहीं — ताकि
model में कोई खाना जोड़ना भूल जाएँ तो भी backup अधूरा न हो।

backup का version `1.0.0` → `2.0.0`, पर **पुरानी फ़ाइल भी चलती है**।

## 2. Restore अब सुरक्षित

पहले वह **पहले `delete` करता था, फिर डालता था**। बीच में कुछ टूटे तो किसान
का data मिट चुका होता और नया आया नहीं होता।

अब — पहले पूरा पढ़ो और जाँचो, तभी हाथ लगाओ:
- ख़ाली/टूटी फ़ाइल पर **कुछ छूता ही नहीं**
- सिर्फ़ उन्हीं tables को हाथ लगाता है जो फ़ाइल में सचमुच हैं
  (पुरानी 1.0.0 backup से पशु मिटते नहीं — वे उसमें थे ही नहीं)

## 3. फ़ोटो

- `pashu_photos` अब backup rules में है (पहले **छूट गया था**)
- DB में अब सिर्फ़ **फ़ाइल का नाम**, पूरा रास्ता नहीं
- migration (v8) पुराने रास्ते ख़ुद छोटे कर देता है

## 4. `onDowngrade` लगा

ख़ाली handler। ⚠️ `onDatabaseDowngradeDelete` **नहीं** लगाया — वह पूरा
database मिटा देता है।

## 5. रास्ते में मिली दो और बातें

**`dairy_product_entries` का DDL दो जगह लिखा था** — `_onCreate` में और
`_onUpgrade` में। दोनों अलग हो जाने का पूरा ख़तरा था (नए install पर एक तरह
का table, update पर दूसरी तरह का)। अब **एक ही जगह** है।

**`_onUpgrade` अब ख़ुद को ठीक करता है** — किसी किसान का migration बीच में
टूटा हो, या backup से अजीब version आ गया हो, तो अगली बार ऐप खुलते ही छूटे
हुए tables बन जाते हैं।

## 6. Google Drive backup

किसान की **अपनी Drive** के छिपे फ़ोल्डर में, ऐप बंद करते समय। पूरी विधि
`GOOGLE_SETUP.md` में। Console setup तक कोड चुप रहेगा।

## 7. हफ़्ते वाली WhatsApp याद

जिनका Google खाता नहीं जुड़ा, उन्हें **हर रविवार सुबह 10 बजे**। खाता जुड़ते
ही अपने आप बंद।
